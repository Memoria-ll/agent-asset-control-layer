**AACLの設計更新 — Skillの段階的読込、Workflowへの分類、モデル未指定、作成・エクスポート用Skill**

2026年9月9日。ユーザーによる6点の補足を踏まえた設計方針です。[導入と資産の紐づけの設計案](mcp-first-onboarding-and-asset-relations.md)を更新する内容です。実装結果と検証範囲は[実装確認表](improvement-implementation-2026-09-09.md)、操作方法は[運用ガイド](mcp-operations.md)に記載しています。

**Skillは現在の担当者が使う手順・知識、Workflowは担当者への委譲と工程の制御を表します。** Roleは担当する責務です。Modelは任意に指定できる実行条件であり、RoleやWorkflowの利用に必須の設定にはしません。Runtimeはサブエージェントを起動する実行環境です。

以下では、ユーザーが示した方針と、それを成立させるための推奨動作を区別します。

**1. Roleには、その責務で利用できるSkillを紐づけます**

ユーザーの方針として、実装Roleには実装に関するSkill、設計Roleには設計に関するSkillを紐づけます。実行時には、そのRoleと今回の条件に必要な情報だけを渡します。

Skillについて最初に渡す情報は、利用場面を判断できるdescriptionです。識別と取得に必要な名前・ID・取得先を添えます。Skill本文や補助ファイル、依存するSkillの本文まで最初から読み込みません。必要と判断したSkillをMCPで取得して使います。

| 情報                                             | 渡すタイミング                                                                     |
| ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 現在のRoleの責務、今回の対象、制約、必要な成果物 | 担当作業を始める際に渡します。                                                     |
| 適用するRuleの指示本文                           | 守る必要がある時点までに渡します。Skillのdescriptionだけを渡す方式とは区別します。 |
| 利用候補のSkillの名前・ID・description・取得先   | Roleと今回の条件に応じた一覧として渡します。                                       |
| Skill本文、必要な補助ファイル                    | 実際にそのSkillを使う際に取得します。                                              |
| Skillから参照する別のSkill                       | 参照・利用が必要になった時点で取得します。                                         |

RoleとModelの両方から選ばれたSkillは、一覧でも本文でも重複させません。選ばれた理由は保持します。descriptionを見ただけのSkillと、本文を取得して作業に用いたSkillは、観測上も区別します。

MCPの通常応答にもこの方針を適用します。本文の注入を避けても、一覧や解決結果の付随情報に全本文が入っていれば、同じ量をAIへ渡すことになります。詳細な診断情報は別途取得できるようにします。

**2. 取り込み元のフォルダ名は、分類を決める根拠の一部として扱います**

ユーザーの指摘を採用し、skillsフォルダにあることだけを理由に、AACLのSkillへ確定しません。既存環境では、担当者への委譲や工程管理をSkill形式で表している可能性があるためです。

取り込み時には元ファイルと出所を保存し、AIが実際の振る舞いを読んで分類します。otherの整理だけでなく、Skillに見える取り込み候補も、この確認の対象です。

| 内容の例                                                             | AACLでの扱い                                                                |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 現在の担当者が調査・実装・確認を進める手順や専門知識                 | Skillにします。複数の手順があるだけではWorkflowにしません。                 |
| 別の担当者へ仕事を渡し、結果を待ち、レビューや差し戻しを制御する手順 | Workflowにします。担当者の責務をRoleとして表します。                        |
| 特定の担当者の責務や判断基準                                         | Role、またはそのRoleに適用するRule等として整理します。                      |
| モデルに応じた補足指示                                               | 任意のModel条件に適用するRule等として整理します。                           |
| 上記が一つのファイルに混在しているもの                               | Workflow・Role・Skill等へ必要に応じて分解し、同じ移行元との関係を残します。 |

例えば「設計担当へ仕様を依頼し、実装担当へ渡し、レビュー担当の指摘があれば戻す」という資産は、Workflowとして表現します。各担当者が使う個別の作業手順が同じ原文にあれば、その部分はSkillとして分けられます。元ファイル一つに対して、出力資産を一つに限定しません。

分類は実際の動作に基づきます。文章中でWorkflowを説明しているだけの場合や、使わない方法を例示している場合を、工程制御と取り違えないようにします。

変換後は、元の指示と構造化したWorkflowを両方有効にして二重に委譲する状態を避けます。元の適用範囲、成果物、差し戻し条件を保持し、変換できなかった部分は明示します。導入時に認められた範囲では、分類と変換を自動適用して結果をまとめて報告します。

**3. モデル未指定では、実行環境の標準設定でサブエージェントを起動します**

ユーザーの方針として、サブエージェントを利用できる実行環境を前提にし、Modelの割り当てを必須にしません。

本資料の推奨は、**AACLにモデル指定がなければ、モデル指定を付けずにRuntimeへ担当Roleの起動を依頼する**ことです。Roleの責務、必要な作業情報、利用候補のSkill、成果物と完了条件は引き継ぎます。

同じモデルでも、別のサブエージェントへRoleごとの情報を渡すことで、設計担当とレビュー担当を分けられます。モデルを変えることを、担当を分けるための条件にしません。

| 状態                                                       | 推奨する動作                                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 今回の実行・工程・Roleのいずれにもモデル指定がありません。 | Runtimeの標準設定でサブエージェントを起動します。モデル登録不足を理由に開始を拒否しません。                      |
| 今回の実行や保存済み方針でモデルが明示されています。       | 利用可能なら指定を使います。今回の明示指定、工程の設定、Roleの既定設定の順を基本にし、必須制約は別途検証します。 |
| 明示モデルをRuntimeが選択できない、または利用できません。  | 指定を満たせないことを返します。事前に認めた代替方針がある場合だけ、その方針で継続します。                       |
| Runtimeが実際のモデルを報告できます。                      | 実モデルを記録し、該当するModel固有のRuleやSkill候補を解決します。                                               |
| Runtimeが実モデルを報告できません。                        | モデル不明と記録します。RoleやRuntimeに基づく情報は使い、モデル固有の条件は未評価として示します。                |

Modelが不明な場合も、汎用の作業は開始できます。ただし、特定モデルの使用や異なるモデルによるレビューをWorkflowの必須条件にした場合は、その条件を確認できる必要があります。確認できていない制約を満たしたとは扱いません。

モデル未指定を「必ず親と同じモデル」に置き換えないことを推奨します。親モデルの継承は、Runtimeが表現・保証できる場合に選択できる方針とします。AACLの既定はRuntimeに任せることで、環境ごとの標準動作を利用できます。

モデル固有情報は、実際に担当するサブエージェントについて解決します。親のモデルを、そのまま子の実モデルとして記録しません。可能なら子が作業開始前に自身の実行情報をMCPへ渡し、必要なContextを取得します。子からMCPを使えない環境では、ホストが同等の情報を取得して渡します。

記録上は、ユーザーが指定したモデルと、実際に使われたモデルを分けます。モデル名が報告されても、対応するAACLのModel設定がなければ、モデル固有資産の追加適用はありません。Model設定は追加の使い分けを定義するためのものであり、すべての実行モデルを先に登録する義務にはしません。

**4. Skillには担当者や工程を制御する仕組みを持たせません**

ユーザーの方針を採用し、前の設計案にあった「Skill内の手順を、別の構造化された進行機構として持つ」方向は取り下げます。

Skillに通常の作業手順や条件分岐を書くこと、現在の担当者が別のSkillの説明を参照することは可能です。別担当の起動、担当の切り替え、並行実行の合流、独立した工程状態、担当者間の差し戻しはWorkflowに置きます。

Skill AからBへの紐づけは、同じ担当者がBの知識・手順を必要時に読み出す関係です。Bのために別の担当者を起動する意味は持たせません。

**5. skill-creator相当の汎用Skillで、資産化の相談を受けます**

ユーザーが提案したskill-creator相当の仕組みを、AACLの資産を作成・整理する汎用Skillとして用意する案を採用します。これは本会話で言及されたAACL向けの設計であり、Codexの既存skill-creatorを今回実行したという意味ではありません。

相談・準備の会話でもdescriptionを利用候補に含めます。AIは「このやり方を繰り返し使いたい」「この手順を保存したい」といった依頼に応じて本文を取得します。単なる相談を、無条件に資産の作成や実開発へ進めることはしません。

このSkillは、依頼内容を必ずSkillにするものにはしません。現在の担当者の手順ならSkill、担当者への委譲や工程の管理を含むならWorkflow、と適切な種類を判断して作成します。必要なRoleやRuleを既存資産から再利用し、description、適用条件、参照先、成果物を整えます。

一つの汎用Skillが、複数種類の資産をMCPで作成することは可能です。このSkill自身が別の担当者へ仕事を割り振る必要はありません。複数担当による作成・レビューが必要な場合は、それを別のWorkflowとして定義できます。

初回取り込み、作成用Skill、更新用Skillでは同じ分類規約を使います。UIでの手編集や外部資産の再取り込みもあるため、「作成用Skillを用意したので、以後は混入しない」とは仮定しません。

Coreは、Skillに工程・担当割り当て等の構造を保存しないこと、参照先が存在することなどを機械的に検証します。自然言語本文が担当者の制御を含むかどうかは、整理・作成・変更時のAI確認で扱います。単語の有無だけで分類する規則にはしません。

人間による判断が必要な変更は会話で確認でき、認められた範囲の変更はMCPで完結させます。前に合意した、AIによる承認の自己申告だけに依存しない方針を維持します。

**6. エクスポートは、出力仕様を持つSkillで実行できます**

ユーザーの提案を採用し、出力先ごとのすべての生成処理をCoreに固定することは必須にしません。エクスポート用Skillが、MCPで必要な資産・関係・改訂・補助ファイルを取得し、明文化された出力仕様に従ってファイルを作成する設計にできます。

Coreには、資産を欠落なく取得すること、相互参照と改訂を確認すること、取得中に矛盾した版が混ざらないことを担わせます。形式への変換と配置は、実行環境のファイル操作を利用してエクスポートSkillが行います。必要な補助処理をSkillに同梱することも可能です。

| AACLでの正本    | 出力先での表現                                                                               |
| --------------- | -------------------------------------------------------------------------------------------- |
| Skill           | 出力先が読めるSkill本文、description、必要な補助ファイルにします。                           |
| Rule・Role      | 出力先の指示・担当定義・委譲時の情報など、仕様に定めた形式へ変換します。                     |
| Workflow        | 工程・Role・成果物・差し戻し等を記述したオーケストレーション用SkillやCommand等へ変換します。 |
| Modelの任意設定 | 対応する指定方法があれば変換します。未指定は未指定のまま扱い、モデルを勝手に固定しません。   |

**AACL内部ではWorkflowである資産を、出力先ではオーケストレーション用Skillとして表現できます。** AACLの正本の種類と、Runtimeが受け付けるファイル形式を分けることで、内部のSkillにオーケストレーションを持たせない方針と両立します。

このエクスポート用Skill自身は、資産を読み、ファイルを生成する一人の担当者の手順です。生成する文章に委譲手順が含まれることは、エクスポートSkill自身がその委譲を実行することとは区別します。初回分類でも、実際に従う指示と、作成対象の文例・出力仕様を区別する必要があります。

AACLを停止しても利用を続ける用途では、出力をAACLのMCPへ接続するだけの起動用ファイルに留めません。必要な資産と手順を含め、停止したCoreへの参照が残っていないことを確認します。AACLへ接続して使う生成物も、別の出力目的として明示できます。

出力仕様には、少なくとも次を記載することを推奨します。

- 対象資産と、その依存先をどこまで含めるか。
- 出力先でのフォルダ構造、名前、description、相互参照、補助ファイルの扱い。
- Workflowの工程、委譲、成果物、差し戻し、完了条件の表し方。
- 元の資産ID・改訂と生成ファイルの対応。
- 出力先で表現・強制できない条件の報告方法。
- 既存ファイルとの差分確認と、指定した範囲への配置方法。
- 出力後の構文、参照先、必要なファイルの存在の確認方法。

AIに変換を任せても、出力先で実現できない権限や制約を、指示文へ書いただけで同じ保証になったとは扱いません。実現できる部分と、利用者が選択する必要がある部分を出力結果に示します。

前回の論点である「導入時点への復元だけでなく、最新資産を持ち出せること」は、このエクスポートSkillで満たせます。取り込み元の新しい版を再導入する処理は、既存の取り込み・整理の規約を使います。

**確認する利用シナリオ**

| シナリオ                                                     | 期待する結果                                                                                      |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 実装Roleに複数のSkillが紐づいています。                      | 最初は必要な候補のdescriptionが届き、使うSkillだけ本文を取得します。                              |
| skillsフォルダに、担当者への委譲とレビューの手順があります。 | 内容を確認してWorkflowへ変換し、必要なRole・Skillとの関係を保存します。                           |
| モデルを一度も割り当てていません。                           | Runtimeの標準設定で、Roleごとにサブエージェントを起動できます。                                   |
| 実際のモデルをRuntimeが報告しません。                        | モデル不明を記録し、適用できるRole・Runtimeの情報で作業します。確認できない必須条件は明示します。 |
| モデルを明示したがRuntimeが指定に対応しません。              | 指定を無視せず、利用可能な選択肢か、認められた代替方針を示します。                                |
| 相談中に、繰り返し使う手順の保存を依頼します。               | 作成用Skillが適切な資産種類を判断し、依頼された範囲で作成します。                                 |
| Workflowを別の環境へ持ち出します。                           | 出力先のオーケストレーション用Skill等へ変換し、元Workflowとの対応と変換上の制限を確認できます。   |

この文書にあるモデル未指定時の既定動作や具体的な出力契約は、ユーザーの方向を踏まえた推奨案です。アプリの実装・動作確認や、環境の移行は行っていません。
